# Private Request-Schema Draft — Prospective Transport Prerequisite

> **Status: PROSPECTIVE DRAFT — documentation only.** This document describes a
> future private request protocol sufficient to guide implementation review. It
> does not define production behavior, report parity, authorize a cutover, or
> make any current SDK/HTTP/SSE bridge removable.

## 1. Purpose and boundary

The current transport inventory records that the private worker is an
observation side path and that the extension still relies on the CLI server,
SDK client, and SSE adapter for retained request semantics. This draft fills
only the missing documentation prerequisite: a bounded vocabulary and contract
for a future private request path.

The associated migration work remains Active/residual. This draft does not
complete that phase or its transport gate. The current SDK HTTP/SSE bridge and
all documented bridge responsibilities remain retained until the deletion gates
in §10 are met.

The draft covers the request and mutation classes that must be implemented and
verified before a transport cutover can be considered:

- provider records, provider backend actions, credential checks, and custom
  model discovery;
- session creation, reads, message hydration, prompt submission, lifecycle
  mutations, cancellation, and child-session routing;
- canonical configuration reads, selector materialization, and configuration
  mutations;
- success, failure, cancellation, acknowledgement, retry, reconnect, and
  lifecycle-convergence envelopes shared by those classes.

It does not add a second configuration authority, a second session store, a
credential store in the worker, a compatibility reader, or a replacement for
the existing observation protocol. Observation remains a distinct snapshot /
revision / changefeed surface. The schemas below are wire-shape proposals, not
TypeScript declarations or an implementation commitment.

## 2. Current-state constraints that the draft must preserve

The following are constraints derived from the current inventory and direction
documents, not claims that the draft has been implemented.

| Constraint | Evidence and consequence for this draft |
|---|---|
| The CLI request bridge remains production-required | [Transport bridge inventory](p4.4-g3-transport-bridge-inventory.md) §2 records SDK client construction, server startup/port discovery, SSE delivery, and the retained `KiloProvider` request classes as retained. The proposed protocol cannot be described as their replacement. |
| Canonical selector authority is service-owned | The inventory §3 records `CanonicalConfigService` as authoritative for canonical provider, agent, and configuration selector publication and canonical mutations. Private requests must not create a competing selector/config authority. |
| The private worker currently provides observation only | The inventory §4 cites `observation/snapshot`, `observation/read`, `observation/ack`, `observation/subscribe`, and `observation/changed`. No provider/session/config request handler exists today. |
| Credentials are extension-host-owned | The runtime direction §3/§3.1 assigns credentials to VS Code `SecretStorage`, with opaque references in canonical files. A worker request must never turn the worker or webview into a credential store. |
| Runtime facts are not client-authored | The runtime direction §7.1 makes the runtime authoritative for session existence, lifecycle, message ordering, revisions, and operation outcomes. Clients may observe and request; they may not invent or revise those facts. |
| Config versions are immutable and generation-pinned | The runtime direction §5/§5.1 requires atomic version creation, validation before commit, no active-generation interruption, and version-scoped resource ownership. Config mutation acknowledgements must express those semantics. |
| Current health absence is narrower than transport absence | The inventory §5 records that `/global/health` removal preserves the request bridge and SSE heartbeat/reconnect. No health-absence result is a private request parity result. |

## 3. Carrier and version envelope

The future path may continue to use the existing private JSON-RPC 2.0 stdio
carrier and Content-Length framing. That carrier is intentionally generic; the
semantic contract is the versioned envelope below. Existing `initialize`,
`ping`, `echo`, and observation methods are not silently redefined by this
draft.

### 3.1 Initialization

The worker and extension negotiate the semantic protocol before any domain
request. A worker must reject an unsupported major version and must not accept a
domain request before a successful handshake.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocol": { "name": "kilo-private", "major": 1, "minor": 0 },
    "client": { "name": "kilo-vscode", "version": "<extension-version>" },
    "capabilities": ["provider", "session", "config"]
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocol": { "name": "kilo-private", "major": 1, "minor": 0 },
    "worker": { "name": "kilo-private-worker", "version": "<worker-version>" },
    "capabilities": {
      "provider": ["read", "mutate", "discover-models"],
      "session": ["read", "mutate", "prompt", "cancel"],
      "config": ["read", "mutate"]
    }
  }
}
```

Minor additions must be capability-advertised. A missing capability is a
bounded unsupported operation, not permission to fall back to a different
semantic request. Major-version mismatch is a protocol failure and includes no
domain side effect.

### 3.2 Common request envelope

Every domain request uses a stable operation identity and explicit routing
context. `requestId` identifies one delivery attempt; `opId` identifies the
accepted semantic operation and remains stable across a safe retry or
re-observation.

```json
{
  "v": 1,
  "requestId": "req_<uuid>",
  "opId": "prompt:<message-id>",
  "op": "session/prompt",
  "context": {
    "directory": "/absolute/workspace/path",
    "sessionId": "ses_<id>",
    "parentSessionId": "ses_<id-or-null>",
    "configVersion": 42,
    "sessionRevision": 17
  },
  "idempotencyKey": "idem_<uuid>",
  "payload": {}
}
```

Rules:

1. `v` is the domain-envelope major version. Unknown major versions fail
   before dispatch; unknown fields are ignored only where the operation says
   they are extension-safe.
2. `requestId` is unique for the request delivery. It is not a session ID,
   message ID, config version, or retry identity.
3. `opId` is required for a semantic mutation or generation operation. Reads
   may omit it or use a request-scoped read identity. The operation identity
   must conform to the runtime operation identity rules once the runtime
   implementation is wired.
4. `idempotencyKey` is required for mutations and prompt submission. Reusing
   it with different operation facts is a protocol error. An exact duplicate
   may return the previously recorded outcome without dispatching a second
   side effect.
5. `context.directory` is an absolute, normalized directory identity selected
   by the extension. The worker must reject an absent, relative, or malformed
   directory rather than infer a current working directory.
6. `sessionId` is required for session-scoped operations. A child operation
   carries both the child session and, where relevant, the parent session; the
   worker resolves the directory from the explicit session binding and rejects
   a conflicting directory/session pair.
7. `configVersion` and `sessionRevision` are optimistic freshness guards, not
   client-authored replacements. A stale guard produces a typed stale result;
   it never silently applies against a newer identity.
8. Secret values, access tokens, authorization headers, and serialized SDK
   auth objects are not valid values in `payload`, `context`, or diagnostic
   data. Credential references and bounded credential intents are handled by
   §7.

### 3.3 Common result and event envelopes

JSON-RPC transport success/error remains the carrier-level result. The domain
result is always one of these explicitly discriminated outcomes so a client
can distinguish a successful operation, a rejected operation, cancellation,
and an unknown delivery state.

```json
{
  "v": 1,
  "requestId": "req_<uuid>",
  "opId": "<operation-id>",
  "status": "succeeded",
  "accepted": true,
  "outcome": {
    "type": "succeeded",
    "time": 1730000000000
  },
  "revision": { "session": 18, "config": 42 },
  "data": {}
}
```

The other terminal status shapes are:

```json
{
  "v": 1,
  "requestId": "req_<uuid>",
  "opId": "<operation-id>",
  "status": "failed",
  "accepted": true,
  "outcome": {
    "type": "failed",
    "time": 1730000000000,
    "failure": {
      "code": "provider.unavailable",
      "message": "Redacted bounded message",
      "retryable": true
    }
  }
}
```

```json
{
  "v": 1,
  "requestId": "req_<uuid>",
  "opId": "<operation-id>",
  "status": "cancelled",
  "accepted": true,
  "outcome": {
    "type": "abandoned",
    "time": 1730000000000,
    "cancelledBy": "user_stop"
  }
}
```

`cancelledBy` is a closed initial set: `user_stop`, `steering`, `timeout`,
`network_disconnect`, and `unknown`. A request that was not accepted has
`accepted: false` and no semantic side effect. If delivery is lost after
acceptance and before a result, the client receives an `unknown` delivery
state, not a fabricated failure or success; it must re-observe by `opId`.

Failure data is runtime-normalized and redacted before persistence, projection,
or transport. The draft does not freeze a complete failure taxonomy. At
minimum, failure data has a stable code, bounded message, occurrence time,
retryability decision, and optional bounded diagnostic reference; stack traces,
headers, prompts, and credential material are never panel-visible.

Notifications are revisioned runtime facts, not implicit request responses:

```json
{
  "jsonrpc": "2.0",
  "method": "runtime/changed",
  "params": {
    "v": 1,
    "scope": { "directory": "/absolute/workspace/path", "sessionId": "ses_<id>" },
    "revision": 18,
    "cursor": 204,
    "events": [{ "type": "message.updated", "id": "msg_<id>" }]
  }
}
```

The event payload is bounded and may identify changed records without carrying
full transcript or credential payloads. Snapshot and cursor hydration remain
the authority after a gap, reconnect, or restart; a client never fabricates a
missing event from a request result.

## 4. Operation namespace and routing rules

Names are prospective and intentionally map to current responsibilities. They
do not indicate that a corresponding private handler exists today.

### 4.1 Provider operations

| Operation | Kind | Required context/payload | Result and acknowledgement |
|---|---|---|---|
| `provider/list` | Read | Directory; optional canonical config version | Provider records, connected state, default selection, and an index revision. In canonical mode, selector publication remains derived from canonical service state. |
| `provider/get` | Read | Directory, provider ID | One user-defined provider record or typed not-found. No preset catalog or organization source is implied. |
| `provider/connect` | Mutation | Provider ID, canonical mutation stamp, credential intent or credential ref, provider metadata allowed by the canonical schema | Accepted mutation acknowledgement includes committed config version and provenance; provider readiness is a separate outcome, not a fake config success. |
| `provider/disconnect` | Mutation | Provider ID, canonical mutation stamp, idempotency key | Acknowledgement includes whether the canonical record changed and the resulting config version. |
| `provider/save-custom` | Mutation | Provider ID, canonical provider record without plaintext credential, credential intent/ref as applicable | Validates before commit; success returns the committed version and redacted record projection. |
| `provider/delete-custom` | Mutation | Provider ID, canonical mutation stamp, idempotency key | Success is acknowledged only after the canonical deletion is committed. |
| `provider/authorize` / `provider/oauth-complete` | Mutation | Provider ID, method, bounded OAuth state/code intent; no access token in client payload | The extension-owned credential boundary stores the resulting secret; the wire receives only a redacted outcome and opaque reference metadata. |
| `provider/credential-status` | Read | Provider ID, canonical config version | `available`/`missing`/`invalid` status only. It never returns the credential value. |
| `provider/discover-models` | Read/action | Provider ID or endpoint identity, canonical stamp, credential intent if required | Model records or a typed failure. Discovery does not mutate provider config unless a separately acknowledged mutation is requested. |

Provider listing must not reintroduce preset identities, preset catalogs,
organization config, or cloud onboarding. Generic protocol adapters remain
implementation details of a user-defined provider.

`session/command` is not a distinct lifecycle mutation; it is a `session/prompt` variant that carries a slash-command envelope (`command`, `arguments`, optional `messageID`, `model`/`agent`/`variant`/`parts`) per `SessionPrompt.CommandInput` `session/prompt.ts:2367` and consumer `KiloProvider.ts:4734` `session.command`. Prompt streaming is event delivery associated with the accepted `opId`, not a
series of independently replayable prompt requests. A stream can be resumed by
observation/hydration or marked ambiguous/abandoned by the runtime after a
worker crash; the extension must not silently submit the prompt again.

### 4.3 Configuration operations

| Operation | Kind | Required context/payload | Result and acknowledgement |
|---|---|---|---|
| `config/snapshot` | Read | Directory, optional requested version | Immutable effective snapshot metadata, schema version, config version, provenance, and selector indexes. The snapshot is derived, not a second persisted authority. |
| `config/selectors` | Read | Directory, optional index revision | Provider/model/agent selector indexes from canonical materialization. It is safe to render before worker readiness and does not imply runtime action readiness. |
| `config/read` | Read | Scope (`global`/`project`/`effective`), directory, optional version | Canonical file/asset projection with provenance. Secret values are excluded. |
| `config/write` | Mutation | Scope, field/asset patch expressed in schema vocabulary, base content/version stamp, idempotency key | Validation result, conflict details or committed immutable config version. Stale drafts fail visibly; no silent overwrite. |
| `config/unset` | Mutation | Scope, canonical field/asset identity, base stamp, idempotency key | Schema-defined unset/default result and new version when committed. |
| `config/validate` | Read/action | Candidate canonical records/assets, never legacy overlays | Validation issues with field/file provenance. Validation alone does not commit or alter runtime state. |
| `config/reconcile` | Internal action/event | Canonical file stamp and observed change | New valid version or explicit invalid/stale state. Invalid input preserves the prior valid version and never falls back to legacy values. |

Canonical configuration writes are routed through `CanonicalConfigService` (or
its future private-runtime integration) and must preserve its ownership of
canonical selectors and mutations. The private transport is a carrier, not a
new source class. A cold mutation validates, persists, and acknowledges
immediately after the backend transaction and synchronous side effects. It never
waits for active-generation drain and never interrupts active generations:
affected directories receive a generation-admission fence before persistence,
in-flight generations keep the config snapshot they started with, and new
generations and readers wait until the latest committed-version convergence
lands. Later writes, write-intent operations, and drain-control operations
remain available during convergence and do not queue behind an earlier
convergence. Cold obligations coalesce and are versioned: the pass drains
readers and write/control leases, disposes the exact pre-fence identities,
boots the latest disk state, and releases the fence only after the latest
committed version converges. Reload/load during a fence and runtime shutdown
ownership follow the same fenced model.

## 5. Acknowledgements, ordering, and idempotency

### 5.1 Two-stage mutation acknowledgement

Mutations use a small explicit distinction:

1. **Accepted acknowledgement** — the runtime has accepted the semantic
   operation, assigned/confirmed `opId`, and recorded enough durable state to
   account for it. This does not mean the provider call or generation has
   completed.
2. **Terminal outcome** — the operation is `succeeded`, `failed`, `abandoned`,
   `ambiguous`, or another runtime-approved terminal disposition, with
   occurrence time, redacted failure facts where relevant, and final revision.

Config commits are the exception in timing, not authority: a committed cold
config mutation returns its new immutable config version in the same
acknowledgement without waiting for convergence, but resource convergence and
generation use obey version pinning and fenced latest-version convergence. See
§4.3 for admission-fence, coalescing/versioning, and no-interruption semantics.

`session/cancelQueued` (and `session/abort`) remain drain-control available during that fence via the snapshot-first lane (`drain-control.ts:43,105` `classifyDrainControl` `DELETE /session/:sessionID/queue/:messageID`) and return deterministic `InstanceUnavailableDuringConfigRebuild` 409 when no cached snapshot exists; they operate on the pre-fence runtime, never boot a new instance, never wait for latest-version convergence, and never queue behind an earlier cold write — preserving the established cold-config acknowledgement and convergence contract.

### 5.2 Ordering and stale results

- Every session mutation advances the session revision in the same runtime
  transaction as its durable state change.
- Every config commit advances the config version atomically with canonical
  file/asset persistence and materialization metadata.
- Events carry their scope and revision. The receiver accepts duplicate events
  idempotently, rejects or rehydrates on gaps, and never applies an older
  revision over a newer one.
- A response includes the revision it observed. The extension drops a response
  that no longer matches its request context and rehydrates from the runtime;
  it does not merge stale response data into current UI state.
- A mutation with an already-used idempotency key must return the original
  accepted/terminal facts, or a typed conflict if the supplied operation facts
  differ. It must not dispatch a second provider call, prompt, deletion, or
  config write.

## 6. Failure and cancellation contract

The semantic failure envelope is deliberately smaller than a complete error
taxonomy. It must provide enough information to distinguish:

| State | Meaning |
|---|---|
| `rejected` | The request was invalid, unauthorized for its scope, stale, unsupported, or not accepted. No semantic side effect occurred. |
| `accepted` / `running` | The operation is runtime-owned and may produce events/outcome later. |
| `succeeded` | The operation completed successfully; result data and final revision are authoritative. |
| `failed` | The operation completed unsuccessfully; normalized redacted failure facts are authoritative. |
| `cancelled` / `abandoned` | The runtime recorded cancellation provenance and no client replay is implied. |
| `ambiguous` | The runtime cannot prove the external side effect after a crash/disconnect; the client must re-observe and must not replay automatically. |
| `superseded` | A newer operation or version owns the resulting state; the prior operation remains recorded. |

Cancellation is a request against a runtime operation, not transport disposal
alone. Closing a panel, losing a connection, or killing a worker may trigger a
runtime disposition, but only the runtime records whether the operation was
cancelled, abandoned, ambiguous, or already succeeded. A client-side abort
controller may stop waiting; it cannot rewrite the outcome.

The private runtime owns recovery policy and retry accounting. Nested provider,
SDK, task, or transport attempts must be visible under the owning `opId` and
consume its budget. The client can ask for cancellation and re-observe, but it
cannot schedule a second semantic operation merely because a response timed
out.

`session/fork`, `session/update`, and `session/cancelQueued` reuse the §3.3 versioned envelope (`v`, `requestId`, `opId`, `status`, `outcome`, `revision`, `failure.code`/`retryable`) and §6 distinctions above: a `session/fork` source-not-found or `scope_mismatch` maps to `rejected`, `session/update` `parseSessionTitle` validation maps to `rejected`, and `session/cancelQueued` missing/already-promoted slot maps to idempotent `succeeded false` rather than `failed`; all persist redacted `failure` facts and never echo secret material. `session/command` inherits the same envelope as `session/prompt` variant per §4.2.

## 7. Credential and authorization boundary

The extension host remains the owner of VS Code `SecretStorage`. The following
boundary is required for any implementation of this draft:

1. Canonical provider records contain only an exact opaque credential reference
   and never plaintext keys, headers, OAuth tokens, or environment-variable
   values.
2. Webview messages and persisted selector/config indexes contain no secret
   value. A credential read returns presence/status only.
3. A request may carry a credential reference, a bounded user-intent marker
   such as `credentialRequested: true`, or a provider identity. It may not carry
   an arbitrary secret-storage key or ask the worker to scan SecretStorage.
4. When a provider operation genuinely needs secret material, the extension
   host validates the exact owned reference and resolves it at the narrowest
   host-to-runtime boundary. The value is ephemeral, excluded from logs,
   outcomes, events, persistence, and error messages, and is not echoed in a
   response. An implementation may replace this with an equivalent scoped
   capability/token, but may not move credential ownership to the worker.
5. OAuth authorization codes, callback state, and user-entered credentials are
   single-operation inputs. They are consumed or rejected by the extension-host
   auth boundary and never become general request metadata.
6. Invalid, missing, stale, or unavailable references fail closed with a
   redacted typed failure. No derived key reconstruction, prefix scan, or
   fallback to a legacy credential source is permitted.

Provider authorization is distinct from config mutation authorization. A
successful secret write must be acknowledged separately from provider
connectivity/model discovery, and a failed later provider action must not erase
the prior valid canonical config without an explicit mutation.

## 8. Directory and session identity

The request router must make identity explicit because current extension paths
share one backend while routing directory-scoped state and child sessions.

```json
{
  "directory": "/absolute/canonical/workspace",
  "sessionId": "ses_child",
  "parentSessionId": "ses_parent",
  "configVersion": 42,
  "sessionRevision": 17
}
```

- `directory` is the canonical workspace/request identity, not the panel title,
  process current directory, or a value inferred from a session ID.
- A session binding is established by `session/create` or a runtime-owned
  child-session record. Every later request supplies or resolves exactly one
  binding; mismatches are rejected as `scope_mismatch`.
- Parent-child requests carry the child as the operation target. The parent is
  context for inheritance and provenance only; a parent request cannot mutate
  a child by omission or by using the parent's directory accidentally.
- Provider/config reads use the requested directory and config version. A
  session prompt additionally pins the config version used by that generation.
- `session/fork` (prospective) must carry an explicit target `directory` for the new session (never inferred from the source); current `forkTargetDirectory` `kilocode/server/routes/fork-routing.ts:8` is path-dependent — `workspace-routing.ts:178-186` workspace middleware may resolve before `forkTargetDirectory` handling — with `sourceID`/`sourceDirectory`/`sandboxFallback` inheritance per `Session.fork` `session/session.ts:878`; `Session.ForkInput` `session/session.ts:275` is `sessionID: SessionID, messageID?: MessageID`. `session/update` (rename) targets `sessionID` bound to its `directory` via `UpdatePayload` `session.ts:49`. `session/cancelQueued` targets `sessionID` + `messageID` of the queued slot (`session.ts:113`) and is an `opId`/`idempotencyKey` mutation per §3.2/§5. `session/command` reuses `session/prompt` routing. All four share §3.2 versioned envelope and idempotency guard rules.
- Reconnect and panel/session switch must rehydrate by directory plus session
  identity. No UI-held session fact is authoritative across those boundaries.

## 9. Retry, reconnect, and worker lifecycle

### 9.1 Request delivery states

The client tracks delivery separately from semantic outcome:

| Delivery state | Client action |
|---|---|
| `not-sent` | It may send the request once. |
| `sent-unaccepted` | It may retry the same idempotency key only after the transport implementation proves the request was not accepted, or may re-observe if that cannot be proven. |
| `accepted-unresolved` | It must not replay. Reconnect and query the operation by `opId`. |
| `terminal` | It may display the recorded outcome; an exact duplicate returns the same facts. |
| `transport-unknown` | It must treat semantic state as unknown and rehydrate/query; timeout alone is not failure proof. |

Retry policy is runtime-owned. The private client reconnects the carrier and
performs initialize plus observation hydration; it does not replay accepted
prompts, mutations, provider actions, or cancellations. A request retry must
be bounded, carry the same idempotency key, and be rejected if operation facts
or scope differ.

### 9.2 Restart and convergence handshake

After worker restart, transport reconnect, extension reload, panel close/reopen,
or session switch, the extension performs this conceptual sequence:

1. establish and negotiate the private carrier;
2. obtain the runtime identity/epoch and supported capabilities;
3. hydrate canonical selector/config indexes from the extension-owned canonical
   materialization path, independently of worker action readiness;
4. hydrate runtime observations from a snapshot and the last acknowledged
   cursor/revision;
5. read unresolved operation outcomes by `opId`;
6. subscribe to revisioned events and acknowledge the cursor only after the
   derived read model has applied the snapshot/deltas.

An epoch change invalidates in-memory transport handles, not semantic operation
identities. In-flight operations at a crash receive an explicit runtime
disposition and cleanup fact; they are never silently replayed. A changefeed
gap causes full hydration, not guessed deltas. Reconnect must not erase the
last-known valid selector index or make selector availability depend on worker
readiness.
