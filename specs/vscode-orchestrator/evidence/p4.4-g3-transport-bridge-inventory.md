# P4.4-G3-INV1 Transport Bridge Inventory — Evidence Only

> **Status: EVIDENCE ONLY — no live cutover, bridge deletion, G3 completion, P4.5 work, or P5 work is claimed.**

## Purpose and bound

This independent inventory records the current VS Code extension transport
bridge and the health-absence guards already present in the repository. It
answers one narrow question: which transport paths still carry production
request or liveness responsibilities and therefore cannot be deleted in this
batch.

This batch adds documentation only. It does not modify production transport,
the generated SDK, source-removal matrices, convergence artifacts, trackers,
or tests.

## Current-state conclusion

The VS Code extension still uses the child-process CLI server as its production
request authority for the retained backend request and event paths.
`ServerManager` starts `kilo serve --port 0`, discovers the assigned loopback
port from stdout, and returns the process credentials. `KiloConnectionService`
then creates the SDK client and attaches `SdkSSEAdapter` to the same client. The
request bridge remains necessary for session, prompt, message-history, SDK-only
capability, provider-auth/backend, and fallback/reconciliation paths. It is not,
however, the canonical authority for every selector category: the production
canonical provider, agent, and configuration selector state, its publication
inputs, and its canonical mutations are owned by `CanonicalConfigService`;
`KiloProvider` projects that service-owned state and routes canonical requests to
it.

The removed `/global/health` poll and server health endpoint are separate from
that request bridge. Existing tests prove their absence while also proving
that SSE heartbeat/reconnect and the retained global routes remain. Health
absence is therefore evidence of a bounded narrowing, not evidence that the
HTTP/SSE/SDK bridge is removable.

### Canonical authority versus retained SDK paths

`CanonicalConfigService` is the authority for the canonical provider, agent, and
configuration selector surfaces. Its materialized snapshot and provider/agent
indexes are service-owned (`packages/kilo-vscode/src/config/service.ts:196-207,259-270,310-335,1501-1509`), and its initialization/materialization lifecycle reads and publishes that state (`:489-528`). Its config writes (`:538-570,578-620`), asset writes (`:858-896`), credential-intent processing (`:1230-1304`), and asset deletion (`:1441-1485`) own the corresponding canonical mutation boundaries. `KiloProvider` subscribes to the service and publishes the canonical config/provider/agent projections (`packages/kilo-vscode/src/KiloProvider.ts:525-550,635-778`), while routing canonical provider and config mutations to the service (`:809-1065,1214-1292`; canonical agent mutation at `:3362-3420`).

The retained SDK bridge therefore must not be described as the owner of those
canonical selector branches. In canonical mode, selector publication and
mutation are handled by `CanonicalConfigService`; the corresponding SDK fetch
implementations remain primarily noncanonical/fallback and background
reconciliation support. The SDK bridge also remains the transport for request
semantics that the private observation worker does not implement.

The retained SDK client is not an unused construction artifact. The inspected
`KiloProvider` and related extension paths retain it for the following request
classes:

- session creation, metadata/status refresh, message history, child-session
  synchronization, prompt submission, revert/unrevert, and cancellation;
- SDK-only capabilities such as skills, commands, MCP status, and session-status
  hydration;
- retained provider authentication/backend-action flows, credential/backend
  reads in the legacy or noncanonical branch, and custom-provider model
  discovery;
- fallback and background reconciliation paths. With `CanonicalConfigService`
  attached, provider/agent/config selector publication and mutation use the
  service-owned canonical path, while the related SDK fetch/reconcile
  implementations remain primarily noncanonical/fallback and background
  support (`packages/kilo-vscode/src/KiloProvider.ts:2405-2420`);
- additional sandbox, MCP, image-model, marketplace, and session-usage paths
  using the same client boundary.

The cited paths are sufficient to establish that `createKiloClient`, port
discovery, HTTP request dispatch, and SSE event delivery remain production
dependencies, without treating the SDK as the canonical owner of provider,
agent, or config selector publication/mutation. This inventory does not attempt
to enumerate every SDK method call or every backend endpoint.

## Why bridge deletion is blocked

Deletion is blocked by incomplete canonical private transport coverage, not by
the removed health surface:

1. `CanonicalConfigService` supplies the canonical provider/agent/config
   selector authority, but the extension still needs a production authority for
   retained provider backend actions/auth and credential semantics, custom model
   discovery, session lifecycle, prompt submission, message hydration,
   SDK-only capabilities, and legacy/noncanonical fallback or reconciliation
   requests.
2. The private worker currently defines observation methods only. It has no
   versioned provider/session/config request schemas, response/error contracts,
   authorization and credential boundaries, directory/session routing rules,
   mutation acknowledgement semantics, or equivalent retry/reconnect behavior
   for the retained SDK request classes. `CanonicalConfigService` authority for
   provider/agent/config selectors does not supply those missing session,
   prompt, message-history, SDK-only capability, provider-auth/backend-action,
   or private-worker request semantics.
3. The existing `SdkSSEAdapter` remains the event stream and liveness path for
   the shared SDK client. Removing the client or server discovery without a
   complete replacement would remove the active request and event boundary.
4. Health-absence tests deliberately guard a narrower change: they prevent
   reintroduction of the redundant `/global/health` poll/endpoint while
   preserving the request bridge. They are not a cutover proof.

### Required prerequisites before any bridge deletion proposal

Any later deletion batch would first need, at minimum:

- a canonical private protocol and implementation for every in-scope
  provider/session/config request and mutation path, including typed success,
  failure, cancellation, credential, directory, and session identity
  semantics;
- production wiring from the extension consumers to that private authority,
  with explicit ownership and lifecycle convergence across reconnect, worker
  restart, window/reload, session switch, and panel close/reopen;
- parity tests against the current production behavior for reads, writes,
  prompts, streams/events, retries, stale results, auth handling, and error
  reporting, using real implementation paths rather than duplicated test logic;
- a separately reviewed cutover decision proving that the canonical private
  path is authoritative before removing `createKiloClient`, port discovery,
  HTTP routes, SSE, or generated SDK consumers.

No prerequisite above is implemented or claimed by this inventory.
